## 4. Security audit

### 4.1 Response headers — fixed

All four were **absent** on the SPA, the API and static assets. They are now set on every
response (verified live on `/`, `/api/v1/nodes` and `/assets/index-C4OFHUfJ.js`):

```
X-Content-Type-Options: nosniff
X-Frame-Options: DENY
Referrer-Policy: no-referrer
Content-Security-Policy: frame-ancestors 'none'; object-src 'none'; base-uri 'self'
```

**Why the CSP is narrow.** The bundled front end has **0 inline scripts** and **0 `eval`/
`new Function`**, so a strict `script-src` is plausible — but the bundle is versioned
independently of this repository, and a policy tight enough to be worth having has to be
verified against every release. This policy constrains only what cannot break a page, so it
is safe to ship now. A test asserts `script-src`, `style-src`, `connect-src` and
`default-src` are absent, so adding one later is a deliberate act with a rendering test.

### 4.2 REALITY private key — fixed

`/api/v1/core/config` returned the rendered `config.json` verbatim, which carried
`tls.reality.private_key`. I searched the deployed bundle rather than assuming:

```
references to core/config : let e=await EM.get(`/core/config`); ... o(JSON.stringify(JSON.parse(e.config),null,2))
reality_private           : 0
private_key               : 0
```

The front end only pretty-prints the document for display; it never reads the key. It is now
replaced with a visible placeholder. Redaction is surgical: a document with no key is
returned byte-for-byte, a key outside `tls.reality` is untouched, an unparsable document is
shown as-is, and the account list the page exists to show is preserved.

**Saving cannot be broken by this**, and that is tested rather than asserted: `handleApply`
re-renders from the node and account stores and never accepts a submitted document. A test
posts a placeholder-carrying document to `/api/v1/core/apply` and then asserts the stored
key is still on disk.

An admin session is not the same thing as root. This key is the one field whose disclosure
lets a reader impersonate the node's TLS identity, and it was reaching a browser, a
screenshot and a support paste for no functional reason.

### 4.3 CSRF and session — verified, unchanged

Nothing was loosened. The `X-EasySB-Panel` guard is intact (403 without it, 200 with it),
authentication is still checked before CSRF, and logout revokes only its own session.
`POST /auth/logout` remains a public route but calls `revoke(requestToken(r))`, not
`revokeAll()`, so an anonymous POST cannot end a real session.

**The published v6.0.0 package carries no front end.** Re-checked this round against the
real asset: the published binary contains **0** occurrences of the SPA asset names. So the
release currently in the apt source ships an API and no console — users installing it today
get no UI. The guard added in `7136752` prevents the next release from doing the same.

**Upgrade path, without touching `dpkg` or holding the package:** bump `VERSION` and let the
release workflow build through `make panel` (now guarded) and `pkg-stage` (now guarded). That

replaced by a verified artifact instead of by a silent overwrite. `apt-mark hold` was **not**
applied: it would freeze security updates to fix a packaging problem.

## 8. Not verified

1. **Live node/user create, update, delete and config save through the UI.** They would
   mutate the production account and node configuration that this round was required to
   leave alone. Covered by unit tests, not by live exercise.
2. **A fully strict CSP.** Deliberately not attempted; the narrow policy ships instead.
   Establishing the exact directive set needs a rendering test in CI.
3. **Reboot recovery.** The firewall unit is enabled, idempotent and re-applies at boot, but
   the VPS was not rebooted (no authorisation).
4. **The published `.deb` actually serving a UI.** It cannot — it carries no front end. This
   is a confirmed defect of the current release, not an unknown.
5. **`apt upgrade` end to end** against a new version, since no new version is published yet.

## 9. Rollback

Every change this round is reversible, and the material is on the host.

```bash
# 1. Front end / headers: previous binary
cp /root/easysb-backup-20261010T010309/easysb-pre-final   /usr/bin/easysb
systemctl restart easysb-panel

# 2. Firewall ledger: previous ruleset (only if you want the old rules back)
#    The exact pre-change chain is saved here.
cat /root/firewall-backup-20261010T014433/iptables-nat-PREROUTING.rules

# 3. Firewall unit
systemctl stop easysb-firewall

# 4. Repository: the three commits of this round are 7136752 and 5bde0a5
git -C <checkout> revert --no-edit 5bde0a5 7136752
```

Verified state after any of these: the panel returns to the previous behaviour, the config
is untouched either way, and the node stays up because only `easysb-panel` is restarted for
the binary swap.

**Nothing was pushed, no tag was created or moved, and no release or package was published.**
